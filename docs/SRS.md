# HTML_DBMS/4 — протокол и минимальный UI

Только v4. Legacy 2.x/3.x не поддерживается, сообщения и контейнеры старых версий не читаются.

## Физическое хранилище

```json
{"format":"HTML_DBMS/4","publicHeads":{"Касса":"HEAD64"},"records":{}}
```

`publicHeads` необязательное поле. Отсутствует, пустое или содержит выборочные БД. Каждый `HEAD` — указатель на опубликованный корневой JSON snapshot. Известный извне head позволяет открыть скрытую БД. Каталог публикации не является доказательством последней версии.

`records` — плоский словарь `physicalId → base64url(AES-256-GCM-ciphertext)` для всех JSON-цепочек. Отдельных физических таблиц, каталогов и ролей `main`/`transaction` нет.

## Криптографическая цепочка

Genesis содержит `[null, {"name":"Имя", "parent":null, "state": {}}]`. При создании дочернего документа поле `parent` содержит **выбранный корневой head до добавления** дочернего документа в `$refs`. Для самостоятельной корневой цепочки `parent=null`.

Каждая обычная запись — **ровно три элемента**:

```json
[
  "2026-11-23T18:00:00.000Z",
  "PREVIOUS_HEAD64",
  [{"op":"replace","path":"/F001/name","value":"Новое название"}]
]
```

Это `[timestamp, previousHEAD, operations]`. `seq` не хранится: номер события вычисляется по проверенной позиции в линейной цепочке. Запись не содержит поля `kind`, слова `patch` за пределами стандартных полей `op/path/value`, или обёртки payload. Время — утверждение клиентского устройства, а не криптографически достоверный внешний timestamp. Пустой список Patch запрещён.

Сериализация — UTF-8 от `JSON.stringify(record)`, **без дополнительного сжатия или бинарного сериализатора в v4**. Для `plaintext` вычисляется `H=SHA256(plaintext)` и `AES-key=H`. IV=первые 12 байт `physicalId`, тег GCM 16 байт. `genesisId=first16(SHA256(raw(Hgenesis)))`; `successorId=first16(SHA256(raw(prevID)||raw(prevH)))`, в Base64url. Различающиеся plaintext допускают коллизии successor slot; обычный append возвращает `SUCCESSOR_OCCUPIED`. Только явное подтверждение позволяет физическую перезапись. Чтение не удаляет повреждённые descendants и не скрывает разрыв ancestry.

Детерминированная схема с AES-key=hash содержимого не гарантирует конфиденциальности предсказуемого plaintext, без аудита непригодна для серьёзных секретов.

## Универсальная JSON-модель

Genesis хранит произвольное валидное JSON-состояние. Обычные записи применяют JSON Patch RFC 6902, включая JSON Pointer RFC 6901. Политики предметных таблиц не являются частью криптографического ядра. Базовые операции: genesis / load / inspect / append / pointer / resolve.

Любая криптоцепочка может открываться как корневая. Корневой JSON (если объект) может содержать `name`, `entry`, `$refs`; `$refs` — необязательный словарь `alias → HEAD`, который образует **единственное** пространство имён открытого snapshot. Самостоятельно открытый дочерний документ получает собственный контекст корня. Вложенный `$refs` не затеняет пространство имён выбранного корня.

`{"$ref":"/local/path"}` адресует текущее JSON-состояние; `{"$ref":"funds/F001/name"}` ищет `funds` в **корневом** `$refs` и применяет Pointer `/F001/name`. `funds/` возвращает весь документ. `$ref` разрешается рекурсивно, обнаруживаются отсутствующие имена, ошибки Pointer, циклы и превышение глубины. `entry` может содержать JSON непосредственно либо ссылку. Если после разрешения ссылка ведёт к `{ "type": "application/javascript", "source": "...", "export": "main" }`, оболочка предлагает запуск программы в изолированном sandbox iframe. Произвольные программы не запускаются автоматически и не получают прямого доступа к физическому хранилищу; для чтения и изменения JSON используют ограниченный асинхронный API `read`, `patch`, `createDocument`, `getHead` с подтверждением записи пользователем. Стартовая программа, входящая в сам файл HTML DBMS, записывается при создании БД непосредственно в её `entry`, и только этот неизменённый встроенный образец может запускаться без отдельной команды. Прочее JSON-содержимое `entry` отображается ниже системной панели как данные.

При изменении дочерней цепочки записываются два события: Patch дочернего документа и Patch корневого `/$refs/<alias>`; при успешном staging обновляется соответствующий `publicHeads` только для опубликованной версии. Для скрытой БД новый root head возвращается пользователю, но не объявляется.

## UI: строгая граница оболочки и приложения

Системный интерфейс — **одна узкая верхняя строка** со следующими элементами в указанном порядке:

1. `HTML DBMS`, затем номер версии `4.0.0`.
2. `Новая` — создать новую корневую БД.
3. Выбор существующей БД — **только подставить** `HEAD` в одно редактируемое поле; никакой автоматической загрузки.
4. Поле `HEAD` и кнопка `Открыть`, которая всегда использует **только значение поля**, независимо от выделенного элемента выпадающего списка.
5. `Сохранить` — экспорт физического контейнера в автономный HTML или XML, согласно типу запущенного контейнера.
6. `Инфо` — сворачиваемая служебная панель: сведения о версии и размере хранилища, загрузка другого HTML или XML, копирование HEAD, публикация и скрытие публикации. 
7. `Валидация` — сворачиваемая панель проверок и диагностики: валидность контейнера, криптографических цепочек корня и дочерних JSON, JSON Patch replay, JSON Pointer, историческая непрерывность `$refs`, происхождение генезисов, доверенный исторический HEAD, сравнение с другим HTML или XML **как данными**, диагностика разрывов и отдельное подтверждаемое удаление хвоста с проверенным Recovery HEAD.
8. `Отладка` — read-only просмотр сырой расшифрованной истории выбранного head и известных дочерних цепочек.

**Инфо, Валидация и Отладка скрыты по умолчанию и не относятся к прикладному UI.** Если одна из них раскрывается, другие скрываются. Скрытые цепочки без известного head нельзя объявлять проверенными.

Ни управление документами, ни редактор JSON Patch, ни табличные представления не являются частью системной строки. Остальное пространство под панелями принадлежит вычисленному значению **`entry` корневого JSON**. Стартовый редактор — обычная JS-программа, сериализованная в JSON `entry` при создании БД; это пример, а не системная политика. Если `entry` отсутствует, оболочка показывает лишь нейтральное сообщение.

Исполнение недоверенной программы производится внутри `iframe sandbox="allow-scripts"` без `allow-same-origin`, с ограничивающим CSP. Доступ к чтению/записи осуществляется через документно-ориентированный MessagePort (`MessageChannel`) к явно разрешённому host API; window postMessage используется только для одноразового handshake; операции записи требуют отдельного подтверждения. Это экспериментальный sandbox и не утверждение о полной безопасности против всех браузерных каналов; для защищённого исполнения нужен отдельный аудит.

При экспорте создаётся HTML или XML/XHTML из **чистого исходного шаблона**; в исходный `<script id="db-store">` записывается только сериализованный шифрованный physical store. Отображённые расшифрованные JSON, debug, ввод и состояние DOM не должны попадать в файл.


## 3.0.2 — обязательные инварианты аудита

1. `verifyDatabase(rootHead)` обязан для каждого эффективного root state при replay сохранять все встречавшиеся пары (`alias`, `childHead`), даже если alias исчез из финального `$refs`. Для каждого alias выполняется криптографическое восстановление последнего упомянутого childHead и монотонная проверка ancestry всех предшествовавших ему head. Удаление/повторное добавление alias не сбрасывает baseline; любой rollback/fork — `REFERENCE_ROLLBACK`, никогда не `complete` с warning.
2. Выпадающий список БД **не является состоянием открытия**: он лишь подставляет HEAD, затем возвращается в нейтральный пункт. Открытие через поле HEAD или автоматический путь URL/единственной записи определяет фактический `rootHead`; неудачное открытие прекращает работу старого iframe. Запись запрещена при несовпадении полей HEAD и активного rootHead.
3. Недоверенное `entry` выполняется только в sandbox без `allow-modals` и `allow-same-origin`. Встроенное приложение использует DOM-форму вместо `prompt` для создания документа.
4. При `SUCCESSOR_OCCUPIED` пользователь должен отдельно подтвердить перезапись конкретного физического слота, с предупреждением о потере ancestry. Подтверждение никогда не подменяется молчаливым fallback. Создание/patch выполняются на revision-bound staging overlay с физической delta и частным каталогом; отмена не изменяет основное `records`.
5. Сравнение физического хранилища двух HTML явно перечисляет удалённые (`missingIds`), добавленные (`addedIds`) и изменившиеся (`changedIds`) physical IDs.
6. Панель `Инфо` показывает число сообщений, опубликованных БД и размер JSON-контейнера в байтах.

## Альтернативный автономный XML/XHTML-контейнер (issue #34)

Единый `python3 build.py` обязан выпускать два корректных самостоятельных контейнера:
- `dist/html_dbms.html`, MIME `text/html`, HTML DOM;
- `dist/html_dbms.xml`, MIME `text/xml` или `application/xml`, XML/XHTML DOM с `xmlns="http://www.w3.org/1999/xhtml"`.

`src/core.js`, `src/app.js`, `src/starter.js` являются **единственными** источниками логики. Двух параллельных протоколов, миграций и legacy не существует. JSON UTF-8, genesis, Patch, корневые `$refs`, SHA-256, AES-256-GCM, адреса, `records`, `publicHeads`, ciphertext **одинаковы для обоих контейнеров**. Никакого дополнительного сжатия или байтов кодирования.

XML должен быть well-formed, с закрытыми элементами, XHTML namespace, корректно экранированными атрибутами и CDATA либо экранированный текст для CSS/JS/JSON с сохранением точного textContent и безопасным представлением `]]>`. Непосредственные значения `&`, `<`, `</script>` внутри данных/JSON должны переживать экспорт и повторный импорт. Тип контейнера определяет `XMLSerializer` либо HTML-экспорт; каждый экспорт выполняется только из чистой копии template с заменой `#db-store`.

HTML парсится в инертном template отдельного HTMLDocument; XML — через DOMParser после запрета внешних деклараций и processing instructions. XML с parsererror, неверным namespace или несколькими `#db-store` отклоняется. Импортированный DOM никогда не выполняется; физическое хранилище проверяется и принимается через `adoptStore` (с `validateStore`). Сравнение `missingIds`, `addedIds`, `changedIds` одинаково в обоих вариантах. Права `iframe sandbox="allow-scripts"` и CSP неизменны. При XML DOM создаваемые элементы должны иметь XHTML namespace; в UI допускается только один активный `rootHead`, а выбор каталога лишь заполняет HEAD.

Критерии автоматической приёмки: `tests/dual_build.py`, `tests/browser_dual.py`, core/app/docs тесты, существующая Chromium UI regression; оба файла должны быть воспроизводимо созданы и проверены CI. Browser dual-тест с XML namespace emulation и тестовым крипто-shim **не доказывает** запуск настоящего `file://` XML в Windows. Для этого требуется ручная независимая проверка с реальным Web Crypto и контролем сети; отдельно от исследования безопасности криптосхемы.

## Единый HEAD и URL (issues #35, #37)

`HEAD = Base64url(ID_BYTES || H_BYTES)`: ровно 64 ASCII Base64url символа без padding. Декодировать все 48 байт, затем разделить по смещению 16 байт (16 + 32). Нельзя конкатенировать две Base64url строки или резать HEAD на позиции 22. `packHead`, `unpackHead`, `validHead`, `sameHead` — единый строгий codec. `publicHeads`, `$refs`, `genesis.parent`, предшественник patch, API `getHead`, ответы записи, диагностика и recovery содержат HEAD строкой. Anchor — `anchorHead` полного исторического HEAD, а не отдельного H. Physical `records` по-прежнему адресован 16-байтным ID. SHA-256, GCM и формулы адресов не изменены; изменение plaintext меняет H/ciphertext и последующие HEAD. `/3` несовместим и отвергается.

Приоритет открытия в HTML и XML: `#head=HEAD64` имеет безусловный приоритет. Пустой/повторный/неканонический/недоступный HEAD — ошибка, старый iframe отзывается, fallback запрещён. Без fragment: 0 публичных записей — нейтральный экран; 1 — автоматическое открытие с проверкой `verifyDatabase`; 2+ — ручной выбор. `hashchange` повторяет тот же путь. Запись из старого iframe запрещена. Доверенный стартовый шаблон может запускаться автоматически; остальные JS entry требуют явного запуска.

«Инфо» → «Скопировать ссылку доступа» формирует URL текущей реально открытой версии с `#head=...`, без query. «Подготовить index.html для публикации» из HTML или XML создаёт самостоятельный HTML с пустым `publicHeads`, неизменными ciphertext и без расшифрованного DOM, debug и активного HEAD в экспортируемом файле. Рабочая копия не изменяется. Обычное сохранение сохраняет исходный тип контейнера. Изменения в браузере только локальные; владелец отдельно публикует скачанный `index.html` на статическом HTTPS-хостинге. Ссылка из file:// содержит локальный путь; ссылку для сайта копируют из опубликованной страницы или заменяют базовый URL владельцем.

**Это не авторизация:** fragment обычно не отправляется серверу HTTP, но виден странице, браузеру, истории и получателю ссылки. Все ciphertext доступны скачавшему файл. AES-key = SHA-256(plaintext) допускает офлайн-подбор предсказуемых сообщений. Скрытие каталога не гарантирует конфиденциальности и не отзывает старые snapshots; независимый криптоаудит #4 остаётся необходим.

Проверки: `node tests/core.test.cjs` (реальная криптография и независимые векторы), `python3 tests/browser_head_url.py` (UI, test-only shim), `python3 tests/browser_native_crypto.py` (нативный file:// без shim, отдельно в CI).

Генератор не читает XLSX, старый demo HTML или приватные записи. Старая Excel-derived fixture используется только регрессиями; её сохранённые числовые значения не предназначены для Pages. Workflow `.github/workflows/pages.yml` запускается после успешного Subject tests and build для актуального push в main или вручную на main при наличии успешной проверки того же коммита. Он формирует только `site/index.html`, проверяет его, и публикует через GitHub Pages environment. Первый deploy и последующие изменения синтетического набора требуют явного согласования владельцем SHA-256 содержимого fixture в `examples/cash/pages-approval.json` (формат `{"fixtureSha256":"<64 hex>"}`). Отсутствие файла или несовпадение хеша запрещает deploy. После утверждения неизменного fixture обновления приложения публикуются автоматически при успешном CI. После deploy отдельная проверка сверяет SHA-256 опубликованного файла и запускает браузерный HTTPS smoke. Настройка Pages: Source → GitHub Actions. 

Публичный файл содержит доступный всем ciphertext и публичный HEAD; это не механизм конфиденциального доступа. В публичное окружение никогда не передаются Excel-файлы, старые дампы, HEAD реальных баз или весь репозиторий.

## Стабилизация #41 — этап 1

Базовый размер main fdfbe17a: HTML 66 290 B, XML 66 483 B. Формат /4 пока не меняется: genesis сохраняет name (имя цепочки, не обязательно имя произвольного JSON), parent (явное различие корня и дочернего документа), state. Компактный wire format требует отдельного решения и нового номера, legacy reader не нужен. Genesis шифруется теми же байтами и результатом SHA-256, из которых получен physical ID. На первом этапе обычные root patch и операции с дочерними документами проходили независимый verifier до commit; итоговый checked proof описан ниже; низкоуровневый append остаётся примитивом для физических тестов и явно разрушительных операций. readRecord обращается к одному физическому ID; внешняя структурная проверка проверяет каноничность ciphertext, включая скрытые записи. Открытие передаёт уже проверенное состояние root в renderEntry. Это историческое описание первого этапа; итоговые overlay, контексты, импорт и сборка описаны ниже.

### Стабилизация #41 — этап 2
 
Управляемый store принимается через `adoptStore`, новый создаётся `newStore`. Сериализованный формат /4 неизменен, никакого legacy. Контролируемые словари records/publicHeads проверяют записываемые значения и увеличивают revision. `staging` копирует только каталог и хранит delta физических слотов; доступ к overlay после изменения базовой ревизии или commit запрещён. Commit синхронно применяет проверенную delta, не заменяет весь store. Низкоуровневые genesis/append проверяют ревизию перед мутацией, входные JSON фиксируются до первого await. В окончательной реализации прямой доступ к records отсутствует; контролируемая физическая мутация через Node API отзывает proof.

Внутренний proof хранит state выбранного root и последнюю проверенную версию каждого исторического alias, в том числе удалённого. При обычном append проверяются новые события и изменённые refs; физическая перезапись вызывает независимый verifier. Полная проверка `verifyDatabase` заново дешифрует и проверяет историю, не принимает proof как доказательство; исторические refs собираются в том же replay. Системное чтение использует проверенное состояние, наружу выдаются копии. Внешние read операции принимают единый snapshot. ### Wire format: решение по genesis

Сохраняется `/4`: `[null,{name,parent,state}]`, поскольку это однозначная метаинформация цепочки даже при произвольном scalar/array JSON. Позиционное предложение `/5`: `[null,name,state]` для корня и `[null,name,state,parentHEAD]` для дочернего genesis сохраняет различие с patch по первому элементу и связь с родителем. Для имени «Касса» и state `{}` это экономит 31 байт plaintext на корне (53 → 22); с 16-байтным GCM tag Base64url ciphertext сокращается с 92 до 51 символа (41 символ). Это отдельное несовместимое решение, не требуется для исправления целостности или минимизации пустого контейнера. Номер `/4` не переопределяется; legacy reader отсутствует. Решение о `/5` можно принять до первого релиза отдельно от текущих оптимизаций.


Заключительная стабилизация: после принятия store исходный `db-store` очищается до создания чистого export template; ciphertext хранится только приватным ядром. Скрытие debug очищает вывод, а скрытая панель не начинает inspect при commit. Для оболочки действует единый лимит 256 МиБ: staged commit и принятие импорта проверяют размер актуального store по инкрементальному счётчику, с учётом размера экспортного шаблона и консервативной надбавки на escaping имён публикаций. Экспорт дополнительно проверяет фактический размер Blob до скачивания. При открытии внешнего файла напрямую ограничивается размер будущего экспорта, а не размер произвольной исходной разметки. Низкоуровневый `publish()` проверяет структуру и CAS каталога, а не ancestry; штатная оболочка предварительно проверяет публикуемую БД либо использует результат проверенной транзакции. RPC не экспортирует этот примитив.


Заключительная сборка с ограничением размера и устранением скрытого debug replay: HTML 56 453 Б, XML 56 624 Б (+411 Б к третьему этапу). Синтаксический аудит конечного контейнера выполняется в `tests/dual_build.py`: парсинг HTML/XML и вложенного markup, AST JavaScript (Acorn из зафиксированного lockfile), проверка CSS синтаксическим нормализатором, отрицательные контроли комментариев. Эти проверки остаются частью release gate; наличие тестов не равно успешной приёмке. Двусторонний root oracle: 5 принятых и 6 отклонённых кандидатов дополнительно к 76/37 прежних сценариев. ## Ресурсная целостность #46 (draft)
Протокол /4 и физическая запись 12 МиБ неизменны. Предложенная runtime policy: материализованное JSON 8 МиБ UTF-8, 100 000 значений (ключи не узлы), глубина 32; запись до 200 000 значений.
