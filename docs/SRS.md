# HTML DBMS — спецификация требований к программному обеспечению, экспериментальный протокол 2.1

**Состояние:** рабочая спецификация до первого стабильного релиза. Документ использует принципы инженерии требований Вигерса и Битти: уникальные идентификаторы, проверяемые условия, прослеживаемость и явные границы качества. Все требования сформулированы для HTML DBMS самостоятельно.

## 1. Назначение и границы

**BG-01.** Пользователь должен иметь возможность вести переносимую структурированную БД в одном автономном HTML-файле без отдельного сервера и установки СУБД.

В границах версии 2.1: единый HTML-контейнер, несколько логических цепочек в одном физическом JSON Object, SHA-256, AES-256-GCM, детерминированные физические адреса, детерминированный genesis, JSON Pointer RFC 6901, JSON Patch RFC 6902, append-only транзакционная цепочка и проверка истории по доверенному hash anchor.

Вне границ: гарантированная конфиденциальность предсказуемого plaintext, авторство, распределённый консенсус, разрешение криптографических коллизий, автоматическая миграция экспериментальных форматов, совместимость с 2.0, полноценный импорт Excel, формулы, графики и jsonRVM.

## 2. Бизнес-правила и архитектурные инварианты

- **BR-01.** Ранее записанная транзакция не изменяется и не удаляется; исправление — новая запись.
- **BR-02.** Существующий физический ключ `records[ID]` никогда не перезаписывается.
- **BR-03.** Один predecessor `(IDprev, Hprev)` определяет ровно один допустимый физический адрес successor.
- **BR-04.** Содержимое genesis определяет семантическую идентичность логической цепочки.
- **BR-05.** Повторная инициализация тем же genesis не создаёт новый корень; она распознаёт уже существующую цепочку.
- **BR-06.** Если создателю нужна независимая или непредсказуемая идентичность цепочки, различающие данные, включая случайный nonce, помещаются в сам genesis.
- **BR-07.** До первого стабильного релиза легаси-совместимость не поддерживается. Экспериментальный формат заменяется целиком.
- **BR-08.** Хэш из самого проверяемого HTML не является доказательством происхождения; внешняя проверка требует независимо доверенного anchor.

## 3. Формат контейнера

Контейнер версии 2.1:

```json
{
  "format": "HTML_DBMS/2.1",
  "publicHead": null,
  "records": {}
}
```

`records` — JSON Object. Каждый ключ — 22-символьный Base64url от 16-байтового физического ID. Каждое значение — Base64url ciphertext AES-GCM. Оболочка `{iv,ct}` запрещена в 2.1.

Контейнер с `format`, отличным от `HTML_DBMS/2.1`, должен отвергаться. Код 2.1 не должен содержать мигратора, fallback-чтения 2.0 или смешанного режима.

## 4. Формат сообщения

Полное сообщение:

```text
[seq, kind, time, prev_key, prev_hash, payload]
```

Для genesis:

```text
[1, "genesis", null, null, null, {policy, state}]
```

Для последующих событий:

```text
[n, "patch", ISO-UTC-time, IDprev, Hprev, {patch:[...]}]
```

Поле версии отсутствует в каждом сообщении, поскольку версия задаётся контейнером. Genesis не получает автоматически время или случайное значение: это необходимо для детерминированной идентичности цепочки.

## 5. Криптографическое преобразование

Для сообщения `P_i`:

```text
H_i = SHA256(UTF8(JSON.stringify(P_i)))
K_i = H_i
```

`K_i` используется как 256-битный ключ AES-GCM.

Физический ID genesis:

```text
ID_0 = B64URL(first16(SHA256(raw(H_0))))
```

Физический ID successor:

```text
ID_i = B64URL(first16(SHA256(raw(ID_{i-1}) || raw(H_{i-1}))))
```

`raw(ID)` имеет длину 16 байт, `raw(H)` — 32 байта. Внутри successor сохранены оба значения предшественника, что позволяет проверить вычисленный физический адрес.

IV AES-GCM:

```text
IV_i = first12(raw(ID_i))
```

Отдельный IV не хранится. Тег аутентификации AES-GCM сохраняется как часть ciphertext и имеет длину 128 бит.

## 6. Функциональные требования

| ID | Требование |
|---|---|
| FR-01 | Система должна открывать и сохранять автономный HTML без внешних скриптов, CSS и обязательной сети. |
| FR-02 | Сохранённый HTML должен содержать полное текущее физическое хранилище и восстанавливать состояние по `publicHead`. |
| FR-03 | Имя скачиваемого файла формируется из заголовка и локальной временной метки. |
| FR-04 | `H_i` должен быть SHA-256 полного сериализованного сообщения и одновременно AES-ключом записи. |
| FR-05 | Genesis должен адресоваться как `first128(SHA256(H0))`, без случайного ID и автоматического времени. |
| FR-06 | Successor должен адресоваться как `first128(SHA256(IDprev || Hprev))`; занятый адрес не перезаписывается. |
| FR-07 | Повторный вызов инициализации с полностью тем же genesis должен вернуть тот же `ID0/H0` и не увеличить число записей. |
| FR-08 | Если вычисленный root ID занят иной записью, инициализация должна завершиться отказом, а не перезаписью. |
| FR-09 | `records[ID]` должен быть строкой ciphertext; отдельные `iv`, `ct`-объекты и legacy envelope не допускаются. |
| FR-10 | IV должен детерминированно выводиться как первые 12 байт физического ID. |
| FR-11 | Перемещение ciphertext под другой ID должно приводить к отказу AES-GCM/проверки адреса. |
| FR-12 | Чтение цепочки должно проверять AES-GCM, SHA-256 plaintext, последовательность `seq`, predecessor ID/hash и вычисленный адрес каждой записи. |
| FR-13 | Несвязанные логические цепочки могут находиться в одном `records` без общего обязательного каталога. |
| FR-14 | Транзакционная цепочка должна допускать только добавление новой строки. |
| FR-15 | Основная цепочка может ссылаться на head вложенной транзакционной цепочки и обновлять ссылку только новым событием. |
| FR-16 | Поддержка 2.0 и других экспериментальных форматов до стабильного релиза запрещена; несовпадающий `format` отвергается. |
| FR-17 | Проверяющий должен иметь возможность подтвердить независимо доверенный исторический hash anchor без исполнения JavaScript из внешнего HTML. |

## 7. Атрибуты качества и безопасность

| ID | Требование |
|---|---|
| NFR-01 | Формат должен быть минимальным: не хранить выводимые служебные данные, включая IV и версию на каждой записи. |
| NFR-02 | Любая ошибка аутентификации, хэша, адреса, ancestry или sequence должна приводить к отказу без частичной записи. |
| NFR-03 | Все операции записи должны быть append-only относительно физического `records`. |
| NFR-04 | JSON Pointer должен отвергать `__proto__`, `prototype`, `constructor`. |
| NFR-05 | Публичный репозиторий содержит только синтетические примеры. |
| NFR-06 | Документация обязана прямо указывать, что `K=SHA256(P)` не защищает предсказуемые сообщения от offline guessing. |
| NFR-07 | Документация обязана указывать, что детерминированный genesis создаёт O(1) membership test для угадываемого инициализатора. |
| NFR-08 | Случайный nonce внутри genesis рассматривается как опциональные пользовательские данные для повышения энтропии, а не обязательная часть протокола. |
| NFR-09 | Настоящие коллизии SHA-256 или 128-битных физических адресов считаются аварийным криптографическим событием; автоматическое «разрешение» коллизии запрещено. |
| NFR-10 | Вся сопровождаемая документация и нормативные формулировки пишутся на русском языке. |
| NFR-11 | Изменения кода, тестов и документации должны быть прослеживаемы до канонических RepoGuard требований. |

## 8. Приёмочные сценарии

**UC-01 — детерминированный genesis.** Два пустых хранилища получают полностью одинаковый genesis. Их `H0`, `ID0` и ciphertext совпадают. Повторная инициализация того же genesis в одном хранилище не добавляет запись.

**UC-02 — различающий genesis.** Изменение любого хэшируемого элемента genesis, включая пользовательский nonce, с подавляющей вероятностью даёт другой `H0` и другой `ID0`.

**UC-03 — линейное продолжение.** Из `(ID_i,H_i)` вычисляется единственный `ID_{i+1}`. Первый successor занимает адрес; конкурирующая запись от того же predecessor получает конфликт и не изменяет `records`.

**UC-04 — связанный IV.** Ciphertext корректно расшифровывается только по своему физическому ID. Перемещение его под другой валидный 128-битный ID приводит к отказу аутентификации.

**UC-05 — старый формат.** Контейнер `HTML_DBMS/2.0` и значение записи вида `{iv,ct}` отвергаются; миграция не выполняется.

**UC-06 — вложенная история.** Основная БД и append-only журнал транзакций сосуществуют в одном физическом `records`, сохраняя независимые head hash.

## 10. Управление изменениями

До первого стабильного релиза экспериментальные форматы могут заменяться несовместимо. После появления стабильного релиза политика совместимости должна быть сформулирована отдельным нормативным требованием; до этого момента отсутствие legacy-кода является сознательным качественным свойством проекта.

Успешные тесты и RepoGuard подтверждают только перечисленные свойства. Они не являются независимым криптографическим аудитом и не доказывают пригодность системы для регулируемых или конфиденциальных данных.
