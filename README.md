# HTML DBMS

**Экспериментальная автономная СУБД в одном HTML-файле.** Файл содержит интерфейс, исполняемый код и JSON-объект зашифрованных хэш-связанных записей. Сохранение создаёт новую самостоятельную HTML-копию.

## Текущий экспериментальный формат: 2.1

Формат 2.1 намеренно несовместим с 2.0. До первого стабильного релиза проект **не поддерживает легаси-форматы, миграцию и смешанные режимы**: минимальность и однозначность протокола важнее обратной совместимости с экспериментальными версиями.

Физическое хранилище имеет вид:

```json
{
  "format": "HTML_DBMS/2.1",
  "publicHead": "...",
  "records": {
    "22-char-base64url-id": "base64url-ciphertext"
  }
}
```

Отдельного поля `iv` нет. Значение `records[ID]` — непосредственно шифртекст AES-GCM вместе с 128-битным тегом аутентификации.

## Запись, хэш и шифрование

Полная запись версии 2.1 сериализуется как:

```text
[seq, kind, time, prev_key, prev_hash, payload]
```

Для genesis используются `seq=1`, `kind="genesis"`, `time=null`, `prev_key=null`, `prev_hash=null`. Время genesis не добавляется автоматически: его содержимое должно быть детерминированным и задаётся только инициализатором цепочки.

Для каждой записи:

```text
P = UTF8(JSON.stringify(record))
H = SHA256(P)
AES-key = H
```

`H` одновременно является хэшем записи, ключом её AES-256-GCM и значением, которое следующая запись хранит как `prev_hash`.

## Физические ID и genesis

Корневая запись адресуется детерминированно:

```text
ID0 = B64URL(first16(SHA256(raw(H0))))
```

Каждая следующая запись:

```text
IDi = B64URL(first16(SHA256(raw(IDprev) || raw(Hprev))))
```

где `raw(IDprev)` — 16 байт, а `raw(Hprev)` — 32 байта. Поэтому один predecessor определяет ровно один допустимый физический адрес следующей записи. Перезапись занятого адреса запрещена.

Одинаковый genesis в одном физическом хранилище означает **ту же логическую цепочку**. Повторная инициализация возвращает существующий корень и не создаёт мусорную запись. Если создателю нужны несколько независимых экземпляров либо непредсказуемая идентичность корня, он должен различить сам genesis — например, включить в его payload случайный nonce.

## IV без отдельного хранения

Для AES-GCM используется:

```text
IV = first12(raw(ID))
```

То есть 96-битный IV выводится из уже существующего 128-битного физического ID и не хранится отдельно. Перемещение ciphertext под другой ID меняет IV и приводит к отказу аутентификации.

Внутри корректной цепочки разные записи содержат разные `seq` и/или разные ссылки на предшественника; их полные сообщения различаются. Ключ AES каждой записи зависит от её полного сообщения. Настоящие коллизии SHA-256 или 128-битных физических адресов рассматриваются как аварийные криптографические события; записи никогда не перезаписываются для «разрешения» такой коллизии.

## Безопасность и осознанные компромиссы

Схема `AES-key = SHA256(plaintext)` экспериментальная и **не гарантирует секретность предсказуемых сообщений**. Если атакующий точно угадывает plaintext, он может вычислить ключ. Детерминированный `ID0` дополнительно делает проверку гипотезы о конкретном угадываемом genesis операцией O(1). Это осознанный компромисс ради полезной семантики `get-or-create` и отсутствия мусорных корней.

Случайный nonce внутри genesis может добавить энтропию и сделать его непредсказуемым, но такой nonce является данными инициализатора, а не обязательным служебным полем протокола.

Публичный `headHash` позволяет читать соответствующую цепочку. Хэш, находящийся внутри недоверенного HTML, подтверждает только внутреннюю согласованность; для проверки происхождения нужен независимо сохранённый доверенный hash anchor. Схема не является протоколом распределённого консенсуса и не проходила независимый криптографический аудит.

## Демонстрация и разработка

Откройте `dist/html_dbms.html` в современном браузере с Web Crypto. Демонстрация содержит только синтетические данные.

- `node tests/core.test.cjs` — протокольные, криптографические, append-only и JSON Patch тесты.
- `node tests/docs-language.test.cjs` — эвристическая проверка русскоязычной документации.
- `python3 build.py` — воспроизводимая сборка `src/index.html + src/core.js + src/app.js` в `dist/html_dbms.html`.

Каноническая спецификация находится в `docs/SRS.md`, требования RepoGuard — в `requirements/html-dbms/`.
