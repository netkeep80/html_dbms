# HTML DBMS

**Экспериментальная автономная СУБД в одном HTML-файле.** Один файл содержит интерфейс, исполняемый код и JSON-объект зашифрованных хэш-связанных записей. Сохранение создаёт новую самостоятельную HTML-копию.

## Текущий экспериментальный протокол: 2.2

Версия 2.2 намеренно несовместима с 2.1. До первого стабильного релиза проект не поддерживает легаси-форматы, миграцию и fallback-чтение.

Физическое хранилище:

```json
{
  "format": "HTML_DBMS/2.2",
  "publicHead": ["physical-id", "hash"],
  "records": {
    "physical-id": "base64url-ciphertext"
  }
}
```

`publicHead` допускает три режима:

- `null` — точка входа не опубликована; пользователь должен отдельно указать H либо ID+H;
- `[null,H]` — известен только H, поэтому physical ID ищется по `records`;
- `[ID,H]` — прямое открытие без полного поиска physical map.

Удаление `publicHead` повышает скрытность точки входа, но не является паролем: при угадываемом plaintext значение H может быть вычислено. Для непредсказуемого deterministic genesis можно включить случайный nonce в сам genesis.

## Запись и адресация

Запись имеет форму:

```text
[seq, kind, time, prev_key, prev_hash, payload]
```

Для каждой записи:

```text
P = UTF8(JSON.stringify(record))
H = SHA256(P)
AES-key = H
```

Genesis:

```text
ID0 = B64URL(first16(SHA256(raw(H0))))
```

Successor:

```text
IDi = B64URL(first16(SHA256(raw(IDprev) || raw(Hprev))))
```

IV не хранится:

```text
IV = first12(raw(ID))
```

Значение `records[ID]` — непосредственно AES-GCM ciphertext вместе с тегом аутентификации.

## Занятый successor и версии

Из `(ID,H)` однозначно вычисляется canonical successor slot. Если он свободен, append выполняется обычно. Если он занят, штатный append ничего не изменяет и возвращает `SUCCESSOR_OCCUPIED`.

Занятость slot может означать более свежую скрытую версию, offline fork, чужую запись или повреждение. Пользователь может **явно** подтвердить перезапись. Тогда заменяется только этот `records[IDnext]`; никакой потенциально осиротевший хвост автоматически не удаляется.

Это позволяет выдавать пользователю доступ только к определённой версии через отдельный `(ID,H)`. Пользователь видит, что непосредственное продолжение существует, но без нового H не получает его plaintext.

Если промежуточный slot был перезаписан, старый поздний head остаётся криптографическим свидетелем прежней ancestry. При чтении цепочка остановится в точке, где ожидаемый predecessor больше не расшифровывается под старым H. Система сообщает разрыв и не считает связь с genesis доказанной.

## Genesis и schema транзакций

Genesis является семантической идентичностью цепочки. Он не получает автоматически timestamp или случайный ID. Одинаковый genesis означает ту же логическую цепочку.

Transaction genesis содержит неизменяемое описание строк: заголовок, columns/schema и initial rows. После genesis transaction policy разрешает только добавление новой `/rows/<id>`. Main хранит только operational head вложенной цепочки и не определяет смысл старых транзакций.

Schema проверяется дважды одной логикой: при append и при load/replay. Некорректная историческая строка является признаком некорректной записи, а не просто ошибкой UI.

## JSON-only domain

Протокол принимает только значения, однозначно принадлежащие JSON-domain: `null`, boolean, конечные числа, строки, плотные массивы и plain objects из таких значений.

`undefined`, NaN/Infinity, BigInt, функции, Symbol, циклы, sparse arrays, Date/Map/Set и произвольные экземпляры классов отвергаются до вычисления hash/ID и до commit. Цель: штатный `append` не должен создавать запись, которую последующий `load` не может воспроизвести.

## Диагностика и truncate

`inspect/load` никогда автоматически не исправляют физическое хранилище. Разрыв классифицируется, например, как `MISSING_PREDECESSOR`, `REPLACED_OR_CORRUPTED_PREDECESSOR`, `SCHEMA_VIOLATION`, `SEQUENCE_MISMATCH` или ошибка head.

Удаление повреждённого хвоста выполняется только отдельной явной операцией truncateInvalidTail. Если predecessor невозможно извлечь из повреждённой записи, для восстановления требуется отдельно известный предыдущий operational head. Recovery head обязан непосредственно предшествовать первому диагностированному повреждённому physical slot. Перед удалением диагноз перепроверяется на актуальность. Если slot занят отличающейся записью после overwrite, его ciphertext **сохраняется**, а явно удаляются только диагностированные потомки старой истории.

## Внешняя проверка HTML

Недоверенный HTML разбирается инертным HTML parser. Проверяющий требует ровно один фактический `script#db-store[type="application/json"]` и не исполняет иностранный JavaScript. Это устраняет ошибку regex-привязки, при которой хранилище внутри HTML-комментария могло быть принято за реальное.

Проверка исторического H подтверждает anchored prefix данных, но не авторство последующих событий и не целостность исполняемого JavaScript проверяемого HTML. Любые повторения идентификатора db-store (включая элементы другого типа) отвергаются.

При сохранении HTML используется захваченный до bootstrap исходный шаблон, а не текущий DOM: отображённые таблицы, ID/H, история отладки, поля ввода и диагностика не попадают в файл как plaintext. Единственный переносимый источник состояния — db-store. При publicHead=null runtime capability не публикуется экспортом.

## Безопасность

Схема `AES-key = SHA256(plaintext)` экспериментальная и не гарантирует конфиденциальность предсказуемого plaintext. Практическая безопасность нестандартной конструкции в общей AEAD-модели не доказана. Дополнительная проверка `SHA256(plaintext)=H` после AES-GCM обязательна: известный H является также известным AES-ключом.

128-битный physical ID и SHA-256 коллизии рассматриваются как криптографические аварийные события. Протокол не является распределённым консенсусом. Для provenance нужен независимо сохранённый доверенный H и доверенный verifier.

## Разработка

- `node tests/core.test.cjs` — протокол 2.2, криптоцепочки, access modes, overwrite, schema, JSON-domain, diagnostics и truncate.
- `node tests/app.test.cjs` — регрессии verifier/UI.
- `node tests/docs-language.test.cjs` — русскоязычная документация.
- `python3 build.py` — воспроизводимая сборка `dist/html_dbms.html`.

Нормативные требования находятся в `requirements/html-dbms`, подробная спецификация — в `docs/SRS.md`. Изменения 2.2 зафиксированы в задачах #11–#14.
