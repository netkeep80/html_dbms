# HTML DBMS / 4

Самостоятельная экспериментальная темпоральная NoSQL-СУБД в одном HTML-файле, с криптографически связанными версиями JSON-документов. Один файл может содержать несколько логических БД.

**Сборки одного ядра:** [HTML `dist/html_dbms.html`](dist/html_dbms.html) и [XML/XHTML `dist/html_dbms.xml`](dist/html_dbms.xml). Оба формата автономны, содержат одинаковый протокол HTML_DBMS/4 и запускаются локально в браузерах с поддержкой Web Crypto API. XML предназначен в том числе для пересылки через MAX, который допускает `.xml` (открытие полного контейнера после пересылки через MAX требует отдельной ручной проверки).

## Использование версии 4.0.0

Чистый автономный HTML **намеренно не содержит предустановленных БД**. До первого создания выпадающий список отключён и сообщает «БД отсутствуют». После создания БД она немедленно доступна в текущей вкладке, однако состояние останется только в памяти, пока пользователь не нажмёт **«Сохранить»**. Браузер **скачивает новый HTML-файл и не переписывает** ранее открытый исходный файл. Для повторного открытия следует использовать скачанную копию.

При отсутствии URL HEAD автоматически открывается ровно одна опубликованная БД. При нескольких БД требуется явный выбор и «Открыть», при пустом каталоге ничего не открывается. Кнопка «Открыть» использует только поле HEAD.

Новая БД содержит встроенное стартовое приложение непосредственно в JSON `entry`. Оно **автоматически исполняется** в ограниченном iframe (только для неизменённого доверенного шаблона) и показывает панель «+ Документ / JSON Patch / Обновить» с признаком **«Приложение запущено»**. Исходный JS-код в рабочем представлении корневого JSON скрыт; он доступен в системной «Отладка». Для произвольного JS `entry` нужна явная кнопка запуска.

## Формат HTML_DBMS/4

```json
{
  "format": "HTML_DBMS/4",
  "publicHeads": {"Касса": "HEAD64"},
  "records": {"physical-id": "base64url-ciphertext"}
}
```

`publicHeads` необязателен: может отсутствовать полностью либо перечислять только часть БД. Скрытые БД открываются по известному `HEAD`. `records` — физическое плоское хранилище всех криптографических цепочек; каталог является каталогом публикации, а не наличия или авторизованности.

### Компактные сообщения без `seq`

```json
["2026-11-23T18:00:00.000Z", "PREVIOUS_HEAD64", [{"op":"replace","path":"/x","value":1}]]
```

Формат Patch: `[timestamp, previousHEAD, operations]`. Порядковый номер вычисляется при чтении по длине ancestry и **не сохраняется**. Время фиксируется, но не удостоверяется доверенным источником. Пустой Patch не принимается.

Genesis: `[null,{"name":"...","parent":null,"state":{}}]`. Для дочернего документа `parent` равен head выбранной корневой БД непосредственно перед созданием. Универсальные JSON-цепочки — без `main` и `transaction` политик.

JSON Patch — RFC 6902, локальные JSON Pointer — RFC 6901, `{"$ref":"/path"}` адресует текущий документ, `{"$ref":"funds/F001/name"}` разрешается через `$refs` **выбранной версии** корневого JSON. `entry` может содержать данные непосредственно или ссылку; стартовый редактор хранится в `entry` как JavaScript. Произвольные JS-программы запускаются только по команде в изолированном iframe, операции записи требуют подтверждения.

### Криптография и ограничения

Сериализация: JSON UTF-8; дополнительное сжатие, CBOR и MessagePack в v4 **не включены**. SHA-256, AES-256-GCM, детерминированные генезис- и successor-адреса сохранены; занятый successor не перезаписывается без отдельного подтверждения. Старые форматы 2.x/3.x не открываются и не мигрируются в этом коде.

**Экспериментальная безопасность:** ключ AES в этой схеме производится из SHA-256 исходного содержимого и не гарантирует конфиденциальности предсказуемых сообщений. Для чувствительных данных необходим независимый криптографический аудит.

### UI

В одной узкой верхней строке расположены **HTML DBMS / 4.0**, **Новая**, выбор опубликованной БД, поле **HEAD**, **Открыть**, **Сохранить**, **Инфо**, **Валидация**, **Отладка**.

- Выбор в списке **только заполняет HEAD**. Кнопка **Открыть** использует поле HEAD, а не элемент списка. Изменение поля само по себе не меняет открытую версию.
- **Инфо**: сведения о контейнере и текущем head, загрузка другого HTML, копирование HEAD, публикация/скрытие.
- **Валидация**: проверка контейнера, корневых и дочерних историй, доверенного исторического HEAD, сравнение с внешними HTML/XML как данными, диагностика повреждений и отдельно подтверждаемое восстановление. Скрытые цепочки без известного head невозможно проверить автоматически.
- **Отладка**: просмотр сырых расшифрованных событий в режиме read-only; данные не попадают в экспорт.
- **Всё прикладное содержимое ниже** определяется `entry` выбранного корневого JSON. Новая БД содержит стартовое приложение (JSON viewer/editor, создание документов, JSON Patch), которое запускается в sandbox iframe. Произвольные JS entry исполняются только вручную; запись требует отдельного подтверждения.

## Стабилизация 3.0.2 (аудит)

- Проверка `verifyDatabase` проходит по **всему историческому** `$refs`, включая удалённые позднее документы; rollback через `remove → re-add` отклоняется с `REFERENCE_ROLLBACK`. Проверяются криптографические ancestry всех ранее опубликованных дочерних голов.
- Список опубликованных БД — одноразовый выбор источника HEAD. После выбора он возвращается в пустое состояние; **Открыть** использует только поле HEAD. При ошибке открытия прежний iframe удаляется, а запись при изменённых полях HEAD запрещена до явного нового открытия.
- Кнопка «+ Документ» использует обычную форму с полем имени и начального JSON прямо в `entry`, не вызывает запрещённый в sandbox `prompt()`.
- Конфликт `SUCCESSOR_OCCUPIED` предоставляет **отдельное явное подтверждение** физической перезаписи; при отмене рабочая копия остаётся неизменной. При обновлении дочернего документа подтверждения для дочернего и корневого successor независимы. Прежняя история после такой операции может стать недоступной — это преднамеренное свойство разрешённой физической перезаписи, а не признак успешной проверки старых snapshots.
- Сравнение другого HTML даёт независимые списки `missingIds`, `addedIds`, `changedIds`; панель «Инфо» показывает размер JSON-хранилища в байтах.
- Тесты: `node tests/core.test.cjs`, `node tests/app.test.cjs`, `node tests/docs-language.test.cjs`, `python3 tests/browser_smoke.py` (Chromium + тестовый **небезопасный** crypto shim только для UI). Никакой security guarantee browser smoke не даёт; криптография проверяется Node Web Crypto.

Инварианты стабилизации сохранены в `/4`. Старые wire-форматы не читаются.

## Два автономных формата контейнера (issue #34)

`build.py` преобразует один исходный шаблон и общий `src/core.js`, `src/app.js`, `src/starter.js` в **HTML** и настоящий **XML с XHTML namespace**. Отличается только контейнер DOM/сериализация, **не** `records`, `publicHeads`, `HEAD`, GCM ciphertext или JSON Patch. XML использует CDATA (с разбиением `]]>`) для сохранения исходного текста CSS/JS, а экспорт применяет нативный XMLSerializer. Импорт обоих форматов разбирается DOMParser *как неисполняемые данные*, без вставки импортированного DOM на страницу. В XML-версии `document.createElementNS` создаёт XHTML-элементы, а `hidden` гарантирован CSS-правилом.

Сохранение: HTML→`.html`, XML→`.xml`. Оба варианта могут импортировать и проверять оба формата и переносить физическое хранилище **без единого изменения ciphertext/head**. Экспорт собирается из незаполненного исходного DOM-шаблона, а не из отображённых расшифрованных данных. Уровень sandbox для `entry` не ослаблен.

**Граница подтверждения:** пользователь уже проверил простой XML-пробник в Windows через `file://` (JavaScript, SHA-256, AES-256-GCM, Secure Context). Автоматическое тестирование здесь проверяет XML well-formedness/совместимость сериализации, UI на реальном Chromium c **эмуляцией XML DOM** и отдельно Node Web Crypto для ядра. Тестовый crypto shim **не является** настоящей Web Crypto. Полное выполнение `dist/html_dbms.xml` по `file://` в Windows, без сети и после передачи через MAX, должно пройти отдельную ручную приёмку; не отмечать её PASS без выполнения. Независимый криптоаудит #4 также остаётся открытым.

## Единый HEAD и URL (issues #35, #37)

`HEAD = Base64url(ID_BYTES || H_BYTES)`: ровно 64 ASCII Base64url символа без padding. Декодировать все 48 байт, затем разделить по смещению 16 байт (16 + 32). Нельзя конкатенировать две Base64url строки или резать HEAD на позиции 22. `packHead`, `unpackHead`, `validHead`, `sameHead` — единый строгий codec. `publicHeads`, `$refs`, `genesis.parent`, предшественник patch, API `getHead`, ответы записи, диагностика и recovery содержат HEAD строкой. Anchor — `anchorHead` полного исторического HEAD, а не отдельного H. Physical `records` по-прежнему адресован 16-байтным ID. SHA-256, GCM и формулы адресов не изменены; изменение plaintext меняет H/ciphertext и последующие HEAD. `/3` несовместим и отвергается.

Приоритет открытия в HTML и XML: `#head=HEAD64` имеет безусловный приоритет. Пустой/повторный/неканонический/недоступный HEAD — ошибка, старый iframe отзывается, fallback запрещён. Без fragment: 0 публичных записей — нейтральный экран; 1 — автоматическое открытие с проверкой `verifyDatabase`; 2+ — ручной выбор. `hashchange` повторяет тот же путь. Запись из старого iframe запрещена. Доверенный стартовый шаблон может запускаться автоматически; остальные JS entry требуют явного запуска.

«Инфо» → «Скопировать ссылку доступа» формирует URL текущей реально открытой версии с `#head=...`, без query. «Подготовить index.html для публикации» из HTML или XML создаёт самостоятельный HTML с пустым `publicHeads`, неизменными ciphertext и без расшифрованного DOM, debug и активного HEAD в экспортируемом файле. Рабочая копия не изменяется. Обычное сохранение сохраняет исходный тип контейнера. Изменения в браузере только локальные; владелец отдельно публикует скачанный `index.html` на статическом HTTPS-хостинге. Ссылка из file:// содержит локальный путь; ссылку для сайта копируют из опубликованной страницы или заменяют базовый URL владельцем.

**Это не авторизация:** fragment обычно не отправляется серверу HTTP, но виден странице, браузеру, истории и получателю ссылки. Все ciphertext доступны скачавшему файл. AES-key = SHA-256(plaintext) допускает офлайн-подбор предсказуемых сообщений. Скрытие каталога не гарантирует конфиденциальности и не отзывает старые snapshots; независимый криптоаудит #4 остаётся необходим.

Проверки: `node tests/core.test.cjs` (реальная криптография и независимые векторы), `python3 tests/browser_head_url.py` (UI, test-only shim), `python3 tests/browser_native_crypto.py` (нативный file:// без shim, отдельно в CI).
